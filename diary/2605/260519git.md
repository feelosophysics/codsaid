### b2-2, git branch game

1. 작업하려면, 우선 팀 레포지토리를 clone 한다.
2. 깃허브에서 New issue를 만든다. 이슈를 만든다는 뜻은, 팀 게시판에 '나 이런 내용 작업 할 거야'라는 의미이다. Issue 내용에도 규칙이 있는지는 모르겠다. 깃헙에서 Issue를 만들면 생성되는 '#번호'를 알아둔다. 추후 PR 내용에 적기 위함이다.
3. clone했던 디렉토리에서 새로운 branch를 생성한다. 생성하는 branch 이름에는 규칙이 있다. feature/<name>-<task> 형식을 취해야 한다. 이 규칙은 docs/CONTRIBUTING.md에 문서화 되어 있다.
4. 생성한 branch에서 작업을 한다. 그리고 commit 한다. commit 메시지에도 규칙(컨벤션)이 있다. 'type: subject'의 형식이다. 이 규칙 또한 docs/CONTRIBUTING.md에 문서화 되어 있다.
5. 작업한 branch를 깃헙 팀 레포에 push 한다.
6. 깃헙에서 New pull request 를 생성한다. PR이란, "(팀원들에게)내 작업 리뷰해줘. 특이사항이 있다면 알려주고, 문제가 없다면 main에 merge할 수 있도록 approve해줘."라는 뜻이다. PR도 규칙이 있다. (What, Why, How, Issue: Closes #번호) 네 가지 항목을 충족해야 한다. 이 규칙도 docs/CONTRIBUTING.md에 담겨 있다. 위의 2번에서(Issue만들 때) 생성되었던 'closes #번호'를 내용에 담는다. 그러면, 이 PR이 approve되었을 때 자동으로 연동된 issue가 종료되기 때문이다.

---

- rebase: 브랜치끼리의 작업을 접목하는 방법. 기본적으로 커밋들을 모아서서 복사한 뒤, 다른 곳에 떨궈 놓는 것. 커밋들의 흐름을 보기 좋게 한 줄로 만들 수 있다는 장점이 있다. 저장소의 커밋 로그와 이력이 깨끗해진다. -i(interactive) 옵션을 사용할 수 있다.

- git reset: 브랜치로 하여금 예전의 커밋을 가리키도록 이동시키는 방식으로 변경 내용을 되돌림. 이런 관점에서 '히스토리를 고쳐쓴다'라고 말할 수 있음. 즉, git reset은 마치 애초에 커밋하지 않은 것처럼 예전 커밋으로 브랜치를 옮기는 것.

- git revert: 각자의 컴퓨터에서 작업하는 로컬 브랜치의 경우 reset을 잘 쓸 수 있다만, '히스토리를 고쳐쓴다'는 점 때문에 다른 사람이 작업하는 리모트 브랜치에는 쓸 수 없다. 변경분을 되돌리고, 이 되돌린 내용을 다른 사람들과 공유하기 위해서는 git revert를 써야 한다. / 되돌리려는 변경내역과 정확히 **반대되는** 내용으로 새로운 커밋이 생성된다. revert를 하면 다른 사람들에게도 변경 내역을 밀어(push)보낼 수 있다.

- git commit --amend: 커밋 내용 정정하기

- git fetch: 본질적으로 _로컬_에서 나타내는 원격 저장소의 상태를 실제 원격 저장소의 (지금)상태와 동기화합니다.
    - 원격 저장소에는 있지만 로컬에는 없는 커밋들을 다운로드 받습니다.
    - 우리의 원격 브랜치가 가리키는곳을 업데이트합니다.
    - *fetch는 무엇을 하지 않는가: 여러분의 로컬 상태는 전혀 바꾸지 않습니다. 여러분의 main 브랜치도 업데이트하지 않고 파일 시스템의 모습이던 그 어떤것도 바꾸지 않습니다.

- git pull: git fetch + merge

- git push를 매개변수 없이 사용하는 디폴트 행동은 push.default라 불리는 git의 설정에 따라 결정 됩니다. 이 설정의 기본값은 여러분이 사용하는 git 버전에 따라 다릅니다만, 우리 강의(Learn Git Branching)에서는 upstream을 값으로 사용합니다. 대단한것은 아니지만, 여러분이 프로젝트를 push하기전에 한번쯤 확인해볼 가치가 있습니다.

- git pull --rebase: fetch와 rebase 하는 작업의 줄임 명령어.

- * merge와 rebase 의 trade-off:
    - merge의 장점: 커밋 순서 이력이 보존됨.
    - rebase 장점: 커밋 트리(보이는 히스토리)를 깔끔하게 정리할 수 있음.

- branch에 원격 추적 설정을 하는 방법1
    - git checkout -b totallyNotMain o/main: totallyNotMain이라는 새 branch를 생성하고, o/main을 추적하게 설정.

- branch에 원격 추적 설정을 하는 방법2
    - git branch -u o/main foo: foo branch가 o/main을 추적하도록 설정. 만약 foo가 현재 작업하고 있는 branch라면 git branch -u o/main으로 생략 가능.

- git push에 인자를 넣을 수도 있다.
    - git push <remote> <place>
    - 예시) git push origin main: 내 저장소에 있는 "main"라는 이름의 브랜치로 가서 모든 커밋들을 수집합니다, 그다음 "origin"의 "main"브랜치로 가서 이 브랜치에 부족한 커밋들을 채워 넣고 완료 되면 알려줍니다. / main을 "place"인자로 지정해서 우리가 git에게 어디서부터 커밋이 오는지, 그리고 어디로 커밋이 가야하는지 알려줍니다. 두 저장소간에 동기화 작업을 할 "장소"를 지정해 주는것이라고 볼 수 있습니다. / git이 알아야 할 것은 다 알려줬기 때문에(두 인자를 모두 지정했죠), git은 현재 우리가 체크아웃한 브랜치는 무시하고 명령을 수행합니다.

- git push origin <source>:<destination>: 내가 source와 destination이 다르길 원하면 어떻게 해야되지? 로컬의 foo 브랜치에서 원격의 bar 브랜치로 커밋을 push하고 싶으면 어떻게 해야 되지? / 이것을 일반적으로 colon refspec(콜론 참조스펙)이라고 부릅니다. 참조스펙은 그냥 "git이 알아낼 수 있는 위치"를 이름 붙여서 말하는거에요 (브랜치 'foo'라든가 HEAD~1 라든가) / source와 destination을 따로 지정할 수 있게 되면서, 이제 원격관련 명령어를 좀 멋지고 정확히 사용할수 있게 되었어요. / source는 git이 이해하는 아무 위치를 말합니다. / 만약 여러분이 push하고 싶은 destination(목적지)가 없으면 어떻게하죠? 아무 문제 없어요! git이 만들 새 브랜치 이름을 지어주면 git이 원격 저장소에 새 브랜치를 만들어 줄거에요. git push origin main:newBranch

- git fect origin foo: Git은 원격 저장소의 foo 브랜치로 가서 현재 로컬에 없는 커밋들을 가져와 로컬의 'o/foo' 브랜치 아래에 추가 할 것입니다.

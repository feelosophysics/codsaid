
[Learning Workflow]

1. 미션을 읽는다.
2. ~~평가를 가서, 수행한 사람의 설명을 듣는다.~~ / (이건, 운적 요소.)
3. agent(plan mode 사용), version.1을 만든다. / prompt: *모든 코드에는, 초심자인 내가 다른 초심자에게 설명할 수 있을 정도로, 주석으로 상세한 설명이 포함되어야 합니다. 보너스도 수행합니다.*
4. agent(plan mode), `ultra_detailed_study_guide.md`를 만든다. / prompt: *극한 상세 학습 가이드, 초심자인 내가 다른 초심자에게 설명할 수 있을 정도로, 학습 가이드 로드맵을 수립하고 한 챕터당 약 500줄 정도로(분량이 기니까 우선 1/3만 샘플로, 스타일 확인 후 continue), 밑바닥의 배경 이야기와 함께, 미션의 함의와 워크스페이스(version.1)의 작업물을 이해할 수 있도록 정합성을 따져서, 근본적인 작동방식을 탐구할 수 있도록 "심각할 정도로" 자세하게*
5. 만든 '가이드'를 읽으며, 모르는 부분을 pin point로 LLM과 질의응답한다.
6. '최소한의 학습' 후, 평가(fail)를 받는다. fail이 아닐 정도로 충분히 학습하고 시도했다면 느린 것. / 매칭된 사람과 서로 아는 것을 나눈다. / 학습하며 잘 모르겠는 부분을 물어본다. / 설명하며 자신의 부족한 부분을 체크한다. / 피드백을 듣는다. / 포인트 소진(평가를 가서 설명을 들을 확률 상승)
7. (부족한 부분을 정리한 자료 + 기존의 학습 자료)를 agent에게 주고, '새로운 학습 가이드'를 만든다. / prompt: *"이 자료들을 읽었는데도 모르겠어. 더 상세한 설명이 필요해. 특히 이 부분이 부족하다고 느껴."*
8. '새로운 학습 가이드'로 보충 학습한다.
9. 학습과 평가를 반복한다.
10. 더 효율적인 학습 방법을 알게 되면 개선한다.

### 1. 주요 위험 요소 및 진단

#### LLM 프롬프트의 물리적 한계
* **문제점:** "한 챕터당 약 500줄 정도"와 같이 물리적인 길이를 강제하면, LLM은 무의미한 미사여구를 늘어놓거나, 토큰 제한(Token Limit)에 걸려 중간에 답변이 끊기거나, 앞뒤가 맞지 않는 무리한 비유를 남발할 가능성이 큽니다.
* **진단:** 양적 기준(500줄)보다는 **질적 기준(구체적인 예시, 엣지 케이스, 메모리 구조 등)**을 명시하는 것이 효과적입니다.

### 2. 구체적인 보완 및 개선 제안

위의 진단을 바탕으로 워크플로우를 다음과 같이 보완하는 것을 제안합니다.

#### 개선안 반영 흐름

* **[3단계 변경] 스스로 '설계' 먼저 하기 (AI는 검토용으로)**
  * **기존:** Agent가 Version 1을 만든다.
  * **개선:** **미션을 읽고, 자신이 생각한 구현 논리(의사코드나 설계 흐름도)를 직접 메모장에 적어본 후**, 이를 Agent에게 주고 "이 설계를 바탕으로 에러나 예외 처리를 고려해 Version 1을 구현하고 주석을 달아줘"라고 요청합니다. 
  * *이유:* 최초의 고민 과정이 있어야 AI가 준 코드의 소중함과 차이점을 깊게 이해할 수 있습니다.

* **[4단계 변경] 가이드 프롬프트의 질적 구체화**
  * **기존:** 한 챕터당 500줄 정도로 심각할 정도로 자세하게.
  * **개선:** 물리적 길이 대신 구체적인 분석 관점을 지정합니다.
    * *예시 프롬프트:* `"이 미션의 핵심 CS 이론(또는 아키텍처 구조)을 설명해줘. 특히 1) 발생 가능한 주요 에러와 예외 상황, 2) 메모리/자원 관리 관점에서의 주의점, 3) 이 코드가 작동하는 OS/컴파일러 수준의 배경 원리를 초심자가 이해할 수 있는 비유와 예시 코드를 포함해서 세부 항목별로 나누어 설명해줘."`


# Mini Git 평가 문항

## 평가 개요

| 항목 | 초점 | 평가 방식 |
|------|------|-----------|
| **1** | 기능 구현 | 요구사항대로 동작하는지 |
| **2** | 설계·구조 | 자료구조·책임 분리·재사용 |
| **3** | 이론·알고리즘 | DAG, 탐색, 정렬, 역색인 |
| **4** | 확장·트레이드오프 | 규모·요구 변경·설계 선택 |

---

## 항목 1 · 기능 구현

> 명령어가 스펙대로 동작하는지 확인한다.

### 저장소·브랜치

- `INIT <user_name>` 실행 후 `main` 브랜치, `HEAD`, 현재 사용자 설정이 정상적으로 초기화되어 있는가?
- `BRANCH <name>` 생성 후 `SWITCH <name>`으로 전환되며, 이후 `COMMIT`이 해당 브랜치에 반영되는가?

### 로그·그래프 탐색

- `LOG`가 **부모 커밋이 자식 커밋보다 먼저** 출력되도록 동작하는가?
- `PATH <a> <b>`가 경로가 있으면 최단 경로를, 없으면 `No path`를 출력하는가?
- `ANCESTORS <hashs>`가 모든 조상을 빠짐없이 출력하는가?

### 검색·정렬

- `SEARCH <keyword>` / `SEARCH author=<name>` / `LOG sort-by=date|author`가 요구사항대로 동작하는가?

---

## 항목 2 · 설계·구조

> 구현을 말로 설명할 수 있는지 확인한다.

### 데이터 모델

- 커밋 저장소, 브랜치, `HEAD`, 사용자 정보를 **어떤 구조로 분리**했고, **각 책임**을 설명할 수 있는가?

### 조회·인덱싱

- 커밋 hash로 빠르게 조회하기 위해 **어떤 키-값 구조**를 사용했고, **중복·충돌**을 어떻게 방지했는지 설명할 수 있는가?
- 커밋이 추가될 때 역색인(author/keyword)을 **어떤 시점에, 어떤 방식으로** 갱신하도록 설계했는지 설명할 수 있는가?

### 그래프 로직·문서화

- `LOG`, `PATH`, `ANCESTORS`에서 사용하는 그래프 탐색 로직을 **어떻게 재사용 가능하게** 구성했는지 설명할 수 있는가?
- 주요 함수·클래스에 docstring·주석을 **어떤 기준으로** 작성했는지 설명할 수 있는가?

## 항목 3 · 이론·알고리즘

> 선택한 자료구조·알고리즘의 근거를 설명할 수 있는지 확인한다.

### 커밋 그래프 (DAG)

- 커밋 그래프가 **왜 DAG**여야 하는지, **사이클**이 생기면 어떤 문제가 발생하는지 설명할 수 있는가?
- `LOG`에서 **「부모가 먼저」** 조건을 만족시키기 위해 어떤 접근(예: 위상 정렬 성격의 출력)을 적용했는지 설명할 수 있는가?

### 경로·탐색

- `PATH`에서 최단 경로를 찾기 위해 **어떤 알고리즘**(예: BFS)을 선택했고, **간선을 무방향으로 정의한 이유**를 설명할 수 있는가?

### 정렬·역색인

- 정렬 알고리즘의 **평균·최악 시간복잡도**와 **안정 정렬 여부**를 설명할 수 있는가?
- 역색인이 순회 검색보다 빠른 이유를 **자료구조·시간복잡도** 관점에서 설명할 수 있는가?

## 항목 4 · 확장·트레이드오프

> 요구·규모가 바뀔 때 설계를 어떻게 조정할지 설명할 수 있는지 확인한다.

### 성능·규모

- 커밋 수가 **10배** 늘어났을 때 병목이 될 지점을 예측하고, **개선 방향**(자료구조·알고리즘)을 설명할 수 있는가?

### 요구사항 변경

- `PATH`의 간선 정의를 **「부모 방향만 허용」**으로 바꾸면 결과가 어떻게 달라지고, **구현은 무엇을** 바꿔야 하는지 설명할 수 있는가?
- `LOG sort-by=author` 요구사항이 **「부모·자식 선후도 유지」**로 강화된다면, **어떤 전략**으로 해결할지 설명할 수 있는가?

### 설계 선택

- 해시 생성 방식을 **카운터 기반 → 난수 기반**으로 바꿀 때 **테스트·재현성·디버깅**에 미치는 영향을 설명할 수 있는가?

## 1. 미션의 핵심 함의: 왜 이 고생을 해야 할까요?

지금까지는 혼자 작업했기 때문에 내 맘대로 코드를 고치고 바로 원격 저장소(`main` 브랜치)에 덮어쓰면 그만이었습니다. 하지만 여러 명이 동시에 같은 파일을 수정한다면 어떨까요? 서로의 코드를 덮어쓰게 되어 파일이 망가지거나 서비스가 중단되는 끔찍한 일이 발생할 수 있습니다.

이 미션의 목표는 **"안전하게, 서로의 코드를 리뷰하며, 하나의 완성된 소프트웨어를 조립해 나가는 방법"**을 배우는 것입니다.

*   **PR(Pull Request)과 코드 리뷰:** 내 코드를 바로 프로젝트에 합치지 않고, "이 코드 합쳐도 될까요?"라고 팀원들에게 검사를 맡는 과정입니다.
*   **브랜치(Branch):** 본 프로젝트에 영향을 주지 않고 안전하게 내 작업만 할 수 있는 독립된 평행우주를 만드는 것입니다.
*   **규칙(Convention):** 여러 명이 한 명처럼 작업하기 위해 커밋 메시지, 브랜치 이름 등에 규칙을 정합니다.

## 2. 필수 개념 정복: 브랜치(Branch)와 GitHub Flow

### 2.1 브랜치(Branch)란 도대체 무엇일까?
브랜치는 나무의 '가지'를 뜻합니다. 메인 줄기(`main`)에서 뻗어 나온 곁가지죠.
Git에서 브랜치는 내부적으로 **'특정 커밋(Commit)을 가리키는 얇고 가벼운 포인터(스티커)'**에 불과합니다.

*   **혼자 작업할 때:** 계속 하나의 선(`main`)을 따라 커밋이 쌓입니다.
*   **팀 작업할 때:** `main` 브랜치에서 내 작업을 위한 새로운 브랜치(`feature/my-login`)를 땁니다. 내 브랜치에서 아무리 코드를 망쳐도 `main` 브랜치는 절대 안전합니다! 작업이 끝나면 검사를 거친 후 다시 `main`으로 합칩니다(Merge).

### 2.2 GitHub Flow 전략
현업에서 가장 널리 쓰이는 가볍고 실용적인 협업 전략입니다. 규칙은 아주 단순합니다.

1.  **`main` 브랜치는 항상 완벽해야 한다:** 언제든 고객에게 배포(출시)할 수 있는 에러 없는 상태여야 합니다. (이래서 `main`에 직접 push하는 것을 법으로 금지합니다!)
2.  **새로운 작업은 브랜치를 따서 한다:** 기능 추가, 버그 수정 등은 모두 `main`에서 파생된 새로운 브랜치(`feature/...`)에서 진행합니다.
3.  **작업이 끝나면 PR(Pull Request)을 날린다:** "내 브랜치의 작업을 `main`에 합쳐주세요"라고 요청합니다.
4.  **팀원들의 코드 리뷰를 거친다:** 리뷰를 통해 오류를 잡고, 코드를 개선합니다.
5.  **모두가 동의하면 Merge(병합)한다.**

## 3. Step-by-Step 실전 협업 워크플로우

학습자님은 이제 팀원들과 함께 아래의 순서대로 작업을 진행하게 됩니다.

### Step 1. 저장소(Repository) 세팅 및 보호막 설정
한 명이 대표로 저장소를 만들고, 다른 팀원들을 초대합니다. (Organization을 만들거나 Collaborator로 초대)
**[가장 중요한 설정: Branch Protection Rule]**
GitHub 저장소의 `Settings` -> `Branches`에서 `main` 브랜치 보호 규칙을 설정합니다.
*   *Require a pull request before merging:* 체크! (PR 없이는 합칠 수 없음)
*   *Require approvals:* 체크! 최소 1명 이상 (다른 팀원이 "승인(Approve)"을 눌러줘야만 합쳐짐)
이것이 바로 `main` 브랜치를 안전하게 지키는 방어막입니다.

### Step 2. 팀 규칙 정하기 (`docs/CONTRIBUTING.md`)
협업을 시작하기 전, 다 같이 모여서 규칙을 정해야 합니다. 이 문서가 팀의 헌법이 됩니다.
*   **브랜치 네이밍 규칙:** 예) `feature/학습자이름-작업내용` (ex. `feature/kim-login`)
*   **커밋 메시지 규칙:** 예) `feat: 로그인 기능 추가` (무엇을 했는지 명확히 알 수 있게 접두어 사용)
*   *왜 `update`나 `wip` 같은 메시지를 금지할까요?* 나중에 문제가 생겨 과거 히스토리를 뒤질 때, "무엇을" 바꿨는지 도저히 알 수 없기 때문입니다.

### Step 3. 작업의 시작: Issue 생성
내가 오늘 "A 기능"을 만들 생각이라면, 바로 코딩을 시작하는 것이 아니라 GitHub에서 `Issue`를 만듭니다.
*   **Issue:** "이런이런 작업을 할 예정입니다" 또는 "이런 버그가 있습니다"를 팀에 알리는 게시판입니다.

### Step 4. 브랜치 생성 및 코딩 (명령어의 흐름)
```bash
# 1. 항상 최신 main 브랜치에서 시작합니다.
git checkout main
git pull origin main

# 2. 내 작업을 위한 브랜치를 만듭니다. (Issue #1번을 해결하기 위한 브랜치)
git checkout -b feature/kim-docs-update

# 3. 열심히 코딩하고 파일을 수정합니다.

# 4. 수정한 내용을 스테이지에 올리고 커밋합니다. (정해진 규칙대로!)
git add .
git commit -m "docs: README에 팀 규칙 요약 추가"

# 5. 내 브랜치를 원격 저장소(GitHub)로 올립니다.
git push origin feature/kim-docs-update
```

### Step 5. 대망의 PR(Pull Request) 생성과 코드 리뷰
GitHub 페이지에 가면 방금 push한 브랜치에 대해 "Compare & pull request" 버튼이 생깁니다.
PR 본문을 작성할 때, 미션 요구사항에 따라 **What(무엇을), Why(왜), How(어떻게)**를 자세히 적습니다.
그리고 내용에 `Closes #1` (방금 만든 이슈 번호)를 적어두면, PR이 머지될 때 해당 이슈가 자동으로 닫힙니다! (마법 같은 기능이죠 ✨)

**코드 리뷰란?**
팀원은 학습자님이 올린 PR의 `Files changed` 탭을 보며 코드를 읽습니다.
"여기서 오타가 있네요", "이 부분은 이렇게 고치면 더 좋을 것 같아요"라고 특정 라인에 댓글을 남깁니다.
단순히 "좋아요(LGTM - Looks Good To Me)"만 남기는 것은 팀의 발전에 도움이 되지 않습니다.

## 4. 충돌(Conflict): 두려워하지 마세요, 당연한 겁니다

이 미션의 핵심 중 하나는 **일부러 충돌을 내고 해결해 보는 것**입니다.

### 4.1 충돌은 왜 날까요?
A와 B가 동시에 `main` 브랜치에서 각자 브랜치를 따서 작업했습니다.
두 사람 모두 `README.md` 파일의 **똑같은 줄(라인)**을 수정했습니다.
A가 먼저 PR을 날려서 `main`에 병합(Merge)했습니다.
그 다음 B가 PR을 병합하려고 하면? Git은 멘붕에 빠집니다. "어? A가 이 줄을 사과로 바꿨는데, B는 바나나로 바꿨네? 나는 기계라서 어느 쪽이 맞는지 몰라. **네가 직접 골라줘! (Conflict 발생)**"

### 4.2 충돌 마커 읽는 법
충돌이 난 파일을 열어보면 아래처럼 기괴한 기호들이 추가되어 있습니다.
```text
<<<<<<< HEAD (또는 현재 내 브랜치)
바나나로 수정함
=======
사과로 수정함
>>>>>>> feature/A의브랜치
```
*   `<<<<<<<` 부터 `=======` 까지: 내가 수정한 내용 (또는 병합을 시도받는 브랜치의 내용)
*   `=======` 부터 `>>>>>>>` 까지: 상대방이 수정한 내용

### 4.3 충돌 해결하기 (비자명 충돌)
해결 방법은 아주 단순합니다.
1. 개발자(인간)가 저 기호들(`<<<<<<<`, `=======`, `>>>>>>>`)을 지웁니다.
2. 바나나를 남길지, 사과를 남길지, 아니면 두 개를 합쳐서 '사과와 바나나'로 만들지 코드를 직접 수정해 놓습니다.
3. 수정을 마친 파일을 `git add` 하고 다시 `git commit` 하면 충돌이 해결됩니다!

미션에서는 파일 내용을 수정하는 것뿐만 아니라, **한 명은 파일 이름을 바꾸고 다른 한 명은 그 파일의 내용을 수정하는 등(비자명 충돌)**의 복잡한 충돌도 경험해 보라고 권장하고 있습니다.

## 5. Git 구출 작전: 트러블슈팅 4대장 완벽 해부

실무에서는 "아차!" 하는 순간이 매일 옵니다. 이 4가지 명령어는 여러분의 생명줄입니다. 이 명령어들의 차이를 명확히 이해하는 것이 과제 목표 중 하나입니다.

### A. `git commit --amend` (아차! 오타 났다)
*   **상황:** 방금 커밋을 했는데, 아뿔싸! 메시지에 오타가 있거나, 파일 하나를 깜빡하고 `add` 안 했습니다.
*   **원리:** 가장 최근의 커밋을 뜯어고칩니다.
*   **주의:** **이미 원격(GitHub)에 push한 커밋은 절대 amend하지 마세요!** 로컬에서 나 혼자 가지고 있을 때만 써야 합니다.

### B. `git reset --soft HEAD~1` (시간을 되돌리기 - 로컬)
*   **상황:** 최근 커밋 1개를 아예 취소하고 싶습니다. 하지만 내가 타이핑한 '코드'는 날리고 싶지 않아요.
*   **원리:** 커밋이라는 '포장지'만 뜯어버립니다. 코드는 그대로 남아있어서 다시 `add` 하고 새롭게 포장(commit)할 수 있습니다.
*   **비교:**
    *   `--soft`: 커밋 취소, 스테이지(`add`된 상태) 유지, 코드 유지
    *   `--mixed` (기본값): 커밋 취소, 스테이지 해제, 코드 유지
    *   `--hard`: 커밋 취소, 스테이지 해제, **내 코드도 삭제! (주의)**

### C. `git revert` (시간을 되돌리기 - 원격)
*   **상황:** **이미 GitHub에 push까지 해버렸는데**, 그 코드가 심각한 버그를 일으킵니다. `reset`을 쓰면 원격의 역사와 내 컴퓨터의 역사가 달라져서 팀 전체가 꼬이게 됩니다.
*   **원리:** 과거의 커밋을 지우는 것이 아니라, **"과거의 커밋이 한 행동을 정확히 반대로 하는 새로운 커밋"**을 만듭니다. (플러스를 마이너스로)
*   **왜 쓰는가:** 히스토리(역사)를 조작하지 않고 안전하게 오류를 되돌릴 수 있기 때문에 현업에서 가장 사랑받는 취소 방법입니다.

### D. `git stash` (잠깐 책상 서랍에 넣어두기)
*   **상황:** `feature/A` 브랜치에서 한참 작업 중인데 코드가 엉망입니다. 커밋하기엔 너무 이른데, 갑자기 팀장이 "B 브랜치로 넘어가서 긴급 버그 좀 확인해 줘!"라고 합니다. 커밋 안 하고 브랜치를 옮기면 에러가 납니다.
*   **원리:** 현재 작업 중인 내용을 마치 서랍에 임시로 쑤셔 넣어두듯 보관(`stash`)합니다. 그럼 작업 공간이 깨끗해지고 브랜치 이동이 가능해집니다.
*   **활용:** 버그 해결 후 다시 원래 브랜치로 돌아와서 `git stash pop`을 하면 서랍에서 작업 내용을 다시 꺼내옵니다.

## 6. 문서화의 예술: 우리는 왜 기록을 남기는가

미션에서 `docs/` 폴더 아래에 여러 문서를 남기도록 강제하고 있습니다. 귀찮은 작업처럼 보일 수 있지만, 이는 **"비동기 커뮤니케이션"**의 핵심입니다.

*   `CONTRIBUTING.md`: 새로운 팀원이 합류했을 때, "규칙이 뭐예요?"라고 물어볼 필요 없이 이 문서만 읽으면 바로 적응할 수 있게 해줍니다.
*   `conflict-resolution.md`: 어떤 이유로 충돌이 자주 났는지, 어떻게 합의해서 풀었는지를 기록하면, 다음번에 비슷한 충돌이 날 때 참고할 수 있는 훌륭한 백서가 됩니다.
*   `troubleshooting-log.md`: 누군가 Git 명령어를 실수했을 때 패닉에 빠지지 않도록 도와주는 구급상자입니다.

## 7. 마무리 및 자가 점검

이 가이드를 꼼꼼히 읽고 팀원들과 미션을 수행하셨다면, 처음에 제시되었던 **[과제 목표]**를 스스로 답변해 보세요.

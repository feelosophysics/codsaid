## 1. 신규(Untracked) 파일의 변경 사항 감지 실패 문제

### 🚨 증상
* 새로 생성한 파일이 폴더 내에 존재함에도 불구하고 프로그램 실행 시 `"변경 사항이 없습니다. 커밋/PR 메시지를 생성하지 않고 종료합니다."`라는 메시지가 뜨며 종료됨.

### 🔍 원인
* 프로그램 내부적으로 실행되는 `git diff` 명령어는 **추적 중인 파일(Tracked Files)**의 변경 사항만 감지합니다.
* 새로 만들어져 아직 한 번도 커밋되거나 스테이징되지 않은 신규(Untracked) 파일은 `git diff`에 포함되지 않기 때문에 발생한 현상입니다.

### 💡 해결 방안
* CLI 도구를 실행하기 전에 신규 파일을 `git add` 명령어로 스테이징 영역에 추가합니다.
* 프로그램은 `git diff`에 변경 내용이 없으면 자동으로 `git diff --cached`를 수행하여 스테이징된 변경 사항을 감지하도록 구현되어 있으므로, `git add .` 실행 후 CLI를 실행하면 정상 작동합니다.

## 2. AI API 호출 시 503 및 429 오류 발생 문제

### 🚨 증상
* AI API 요청 중 아래와 같은 에러 로그가 출력되며 실패함.
  * `[ERROR] API 호출 제한 초과 (429 Too Many Requests)`
  * `[ERROR] API HTTP 오류 발생: 503 Service Unavailable`

### 🔍 원인
* **429 (Too Many Requests)**: Google AI Studio의 무료 요금제에서 지원하는 분당 호출 제한(15 RPM) 또는 일일 호출 제한(1500 RPD)을 초과한 경우입니다.
* **503 (Service Unavailable)**: 구글 API 서버에 트래픽이 과도하게 몰리거나 일시적인 서버 점검/불안정 상태인 경우 발생합니다.

### 💡 해결 방안
1. **대기 후 재시도**: 1~2분 정도 대기한 뒤 재실행합니다.
2. **호출 최소화 설계**: 프로그램이 1회 실행될 때 API를 반드시 1회만 호출하도록 제한하고, `commit`과 `pr` 명령어를 분리하여 중복 호출을 예방합니다.
3. **상세 에러 핸들링**: `urllib` 예외 처리부에서 HTTP 상태 코드를 분기하여 사용자가 에러 메시지만 보고도 대기 후 재시도하거나 할당량을 확인해야 함을 인지하도록 보강했습니다.

## 3. Gemma 4 모델 변경 시 404 Not Found 오류 문제

### 🚨 증상
* `--model gemma-4-31b`와 같이 모델명을 지정하여 호출 시 아래와 같은 오류가 발생함.
  * `[ERROR] API 호출 경로를 찾을 수 없습니다 (404 Not Found).`
  * `원인 1: 요청하신 모델('gemma-4-31b')이 단종(Deprecated)되었거나 현재 계정에서 접근할 수 없습니다.`

### 🔍 원인
* Google Gemini API에 등록된 Gemma 4 공식 모델 식별자(Model ID)를 정확히 입력하지 않아 발생한 경로 불일치 오류입니다.

### 💡 해결 방안
* 구글 공식 문서에 명시된 올바른 모델 식별자 명칭으로 수정하여 호출해야 합니다.
  * **올바른 명칭**: `gemma-4-31b-it` (또는 `gemma-4-26b-a4b-it`)
  * `main.py` 파일의 아규먼트 파서 기본값(default)을 `gemma-4-31b-it`로 변경하여 기본 모델 설정을 정비했습니다.

## 4. Gemma 4 모델 연동 시 400 Bad Request 오류 문제

### 🚨 증상
* 모델명을 `gemma-4-31b-it`로 정확하게 기재하고 실행했으나, API 호출 단계에서 아래와 같은 오류가 발생함.
  * `[ERROR] API HTTP 오류 발생: 400 Bad Request`

### 🔍 원인
* **API 파라미터 규격 불일치**: 
  * 기존 Gemini 2.0/2.5 계열 모델의 추론(Thinking)을 비활성화하기 위해 페이로드의 `generationConfig` 안에 `"thinkingConfig": {"thinkingBudget": 0}`를 주입하고 있었습니다.
  * 하지만 Gemma 4 모델 계열은 `thinkingBudget` 속성을 전혀 지원하지 않고 `thinkingLevel` 속성만을 지원하므로, 잘못된 파라미터 전송으로 인해 서버 측에서 `400` 오류를 반환한 것입니다.

### 💡 해결 방안
* 호출 대상 모델명에 `"gemini"`가 포함된 경우에만 `thinkingBudget` 설정을 주입하도록 API 통신 로직을 동적으로 개선했습니다.
* Gemma 모델 계열일 때는 이 설정을 제외하거나, `--thinking-level high` 옵션 지정 시 Gemma의 규격에 맞는 `thinkingLevel: "high"`를 주입하도록 구현을 변경했습니다.

## 5. Gemma 4 실행 시 영어 생각 로그 출력 및 답변 잘림 문제

### 🚨 증상
* Gemma 4 모델 연동 후 정상 결과를 얻었으나, 터미널 출력 결과가 한국어 커밋 메시지가 아닌 영어로 된 개발 생각 과정(Thinking Process)으로 가득 차서 출력되며, 본문이 중간에 끊기는 현상이 발생함.

### 🔍 원인
1. **생각 로그와 답변 파트의 미분리**: 
   * Gemma 4는 추론형 모델이므로 API 응답 시 생각 영역(`"thought": true`)과 최종 답변 영역을 각각 별도의 파트(Part)로 쪼개어 리턴합니다.
   * 기존 코드는 응답 `parts` 배열의 첫 번째 값(`parts[0]['text']`)만 리턴했는데, 이 첫 번째 파트가 바로 영어로 작성된 모델의 생각 로그였습니다.
2. **토큰 한도(maxOutputTokens) 부족**:
   * 생각 로그가 출력 토큰 버퍼를 대부분 채워버리는 바람에, 기본 설정값인 `500` 토큰 한도에 걸려 최종 한국어 답변 파트가 출력되지 못하고 중간에 잘렸습니다.

### 💡 해결 방안
1. **생각 파트 필터링 구현 (`main.py`)**:
   * API 응답 JSON 파싱 시 `thought: True` 속성이 표시된 파트를 제외하고, 순수 답변 파트(`actual_parts`)만 골라내어 문자열로 병합하도록 파싱 코드를 전면 개정했습니다.
2. **기본 토큰 예산 상향 (500 ➡️ 1000)**:
   * 생각 과정과 답변 출력을 모두 온전히 수용할 수 있도록 CLI의 기본 최대 토큰값(`--max-tokens`)을 **`1000`**으로 상향 조정하고 가이드 문서([README.md](file:///Users/f22losophysics1091/Desktop/62api/README.md))를 업데이트했습니다.

## 6. 깃허브(GitHub)에서 중첩된 마크다운 코드 블록 렌더링이 짤리거나 깨지는 문제

### 🚨 증상
* `README.md` 등 마크다운 문서 내에서 다른 마크다운 코드 블록(예: `- **최종 반영 PR (After)**: \`\`\`markdown`)을 작성하고, 그 안에 다시 소스코드 블록(예: ` \`\`\`bash `)을 중첩시켰을 때, 깃허브(GitHub) 웹 화면에서 특정 위치 이후의 내용이 잘리거나 마크다운 형식이 완전히 깨져서 보이는 현상 발생.

### 🔍 원인
* 마크다운 파서가 코드 블록을 해석할 때 백틱의 개수를 기준으로 쌍을 매칭합니다.
* 외부 코드 블록을 3개의 백틱(`` ```markdown ``)으로 감싼 상태에서, 내부 코드 블록을 닫기 위해 3개의 백틱(`` ``` ``)을 사용하면, 마크다운 파서는 이를 내부 코드 블록이 아닌 **외부 코드 블록의 종료 태그**로 오인하여 해석합니다.
* 이로 인해 외부 블록이 원치 않는 위치에서 조기에 닫히고, 이후에 나오는 텍스트가 일반 마크다운으로 풀려버리거나, 문서 마지막에 있는 닫는 백틱 기호가 새로운 코드 블록의 시작 기호로 작동하게 되어 전체 문서 형식을 무너뜨립니다.

### 💡 해결 방안
* 마크다운 규격에 맞춰 **바깥쪽 코드 블록의 백틱 개수를 안쪽 코드 블록보다 더 많게(예: 4개 백틱 ````) 설정**해야 합니다.
* 외부 감싸는 코드 블록 지시자를 ````markdown`으로 시작하고 ````로 닫도록 변경하면, 내부의 3개짜리 백틱(```bash 및 ```) 코드 블록이 충돌 없이 온전히 텍스트(코드)로 내포될 수 있습니다.

## 7. 가상환경 활성화 시 권한 거부(Permission Denied) 문제

### 🚨 증상
* 가상환경 활성화를 위해 `.venv/bin/activate` 명령을 실행했으나, `zsh: permission denied: .venv/bin/activate` 오류가 발생하며 활성화에 실패함.

### 🔍 원인
* `.venv/bin/activate` 파일은 직접 실행하는 바이너리 파일이 아니라, 현재 셸 세션에서 실행하여 환경 변수를 적용하는 **셸 스크립트** 파일입니다. 
* 실행 권한(x)이 없는 상태에서 `./` 경로로 직접 실행하려 했기 때문에 셸에서 권한 거부 에러를 반환한 것입니다.

### 💡 해결 방안
* 셸의 `source` 빌트인 명령어(또는 줄임표 `.`)를 명령어 앞에 명시하여 실행해야 합니다.
  ```zsh
  source .venv/bin/activate
  # 또는
  . .venv/bin/activate
  ```

## 8. 시스템 Alias 설정으로 인해 가상환경 내 파이썬 대신 시스템 파이썬이 실행되는 문제

### 🚨 증상
* `source .venv/bin/activate` 명령으로 가상환경을 정상 활성화했음에도 불구하고, `python` 또는 `pip` 명령어 입력 시 가상환경 내부가 아닌 아이맥 본체(글로벌 시스템)의 파이썬 인터프리터가 작동하는 현상.
* `where python` 실행 시 가상환경 경로보다 `aliased to ...` 형태의 별칭(alias) 설정이 최우선으로 검출됨.

### 🔍 원인
* macOS/Linux의 대화형 셸 환경에서 `python`이나 `pip`가 전역 환경 파일(`.zshrc` 등)에 `alias python=$PYTHON_HOME/bin/python3.12`와 같이 alias로 선언되어 있는 경우입니다.
* 셸에서 alias는 `PATH` 환경 변수(가상환경 활성화 시 수정되는 가상 프로그램 경로)보다 **우선순위가 훨씬 높기 때문에** 가상환경을 활성화했더라도 alias로 지정된 경로가 계속 실행되게 됩니다.

### 💡 해결 방안
* 가상환경 활성화 스크립트(`.venv/bin/activate`) 실행 시 기존 alias를 임시 백업해 두고 해제(`unalias`)한 뒤, 가상환경 비활성화(`deactivate`) 시 복구하도록 개선했습니다.
* `setup.sh` 스크립트를 통해 자동으로 생성/재생성되는 `activate` 코드에 아래의 alias 백업 및 우회 로직을 주입하여 근본적으로 해결했습니다:
  ```sh
  # 활성화 시 백업 후 unalias
  if alias python >/dev/null 2>&1; then
      _OLD_VIRTUAL_ALIAS_PYTHON=$(alias python)
      unalias python
  fi
  
  # deactivate 시 복원
  if [ -n "${_OLD_VIRTUAL_ALIAS_PYTHON:-}" ] ; then
      eval "alias $_OLD_VIRTUAL_ALIAS_PYTHON"
      unset _OLD_VIRTUAL_ALIAS_PYTHON
  fi
  ```

## 9. 가상환경 활성화 시 프롬프트에 괄호가 이중((.venv))으로 표시되는 문제

### 🚨 증상
* 가상환경 활성화 후 터미널 프롬프트 앞에 가상환경 이름이 `((.venv) )`와 같이 이중 괄호로 복잡하게 표현되는 가독성 저하 문제.

### 🔍 원인
* venv 패키지의 기본 `activate` 템플릿 처리 과정 중 `PS1` 환경 변수를 업데이트하는 로직에서 괄호를 중복 랩핑하도록 처리된 사소한 템플릿 구성 버그입니다:
  ```sh
  PS1="("'(.venv) '") ${PS1:-}"
  ```

### 💡 해결 방안
* `.venv/bin/activate` 스크립트 내에서 터미널 프롬프트 변수(`PS1`)를 지정하는 식을 다음과 같이 괄호가 한 번만 적용되도록 깔끔하게 정비했습니다.
  ```sh
  PS1="(.venv) ${PS1:-}"
  ```

## 10. 시스템 파이썬 버전이 낮아 가상환경 생성이 실패하거나 에러가 발생하는 문제

### 🚨 증상
* 가상환경 생성 및 의존성 셋업 과정에서 파이썬 버전이 낮아 문법 에러가 발생하거나 특정 패키지가 설치되지 않고 실패함.

### 🔍 원인
* 본 프로젝트는 Python 3.10 이상 버전에서 제공되는 최신 문법(예: 패턴 매칭 등) 및 최신 라이브러리 규격을 필요로 합니다. 시스템 환경에 구형 파이썬(예: Python 3.9 이하)이 기본값으로 잡혀 있을 경우 가상환경 초기 생성 단계에서 호환성 문제가 유발됩니다.

### 💡 해결 방안
* `setup.sh` 스크립트 내부에서 가상환경 생성 전에 시스템 내에 설치된 사용 가능한 파이썬 바이너리들을 순차 탐색하도록 보강했습니다.
* `python3.13`부터 `python3`까지 돌며 버전이 **Python 3.10 이상**인지 검증한 후, 조건에 부합하는 가장 높은 버전을 선택하여 가상환경을 생성하도록 수정하였습니다:
  ```sh
  PYTHON_BIN=""
  for cmd in python3.13 python3.12 python3.11 python3.10 python3; do
      if command -v "$cmd" >/dev/null 2>&1; then
          ver=$("$cmd" -c 'import sys; print(f"{sys.version_info.major}.{sys.version_info.minor}")')
          major=$(echo "$ver" | cut -d. -f1)
          minor=$(echo "$ver" | cut -d. -f2)
          if [ "$major" -eq 3 ] && [ "$minor" -ge 10 ]; then
              PYTHON_BIN="$cmd"
              break
          fi
      fi
  done
  ```

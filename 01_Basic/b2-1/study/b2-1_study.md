- -m 옵션을 안 쓰고 파이썬 프로그램을 실행시키면 어떻게 돼? 예를 들어, python -m budget_app 대신에 python budget_app을 입력한다면?
- 'CSV가 리스트(List)나 중첩 딕셔너리 표현이 극도로 까다로움.'이라는데, 그럼 가능하긴 하다는 뜻?
- mypy가 뭐야? 타입힌트 설명에서 '이제 이 함수는 자신을 호출할 모든 외부 코드와 아주 단단한 **계약(Contract)**을 맺은 셈이 됩니다.'라는데, 내가 알기로는 타입힌트와 실제 입력되는 인자(매개변수와는 정확히 어떻게 다르지?)의 자료형이 달라도 괜찮다고 알고 있거든. '계약'이라는 단어는 강력한 속박을 뜻하는 어감인데, 사실은 그냥 비유적 표현이야?
- 데이터베이스의 트랜잭션 사상이 뭐야?

### 1. `python -m budget_app` 대신 `python budget_app`을 입력하면 어떻게 되나요?

이 둘의 차이는 단순한 타이핑 방식을 넘어, **파이썬 인터프리터가 모듈과 패키지를 검색하는 경로 설정(`sys.path`) 방식의 차이**에서 비롯됩니다.

#### (1) `python budget_app`으로 실행하는 경우 (디렉토리 직접 실행)
디렉토리명을 직접 지정해 실행하면, 파이썬은 해당 폴더가 일반 폴더인지 패키지인지 깊게 따지지 않고 내부에 있는 `__main__.py`를 찾아 **단독 스크립트**로 실행합니다. 이때 파이썬 내부의 모듈 검색 경로 배열인 `sys.path`에는 다음과 같은 현상이 일어납니다.

* **`sys.path[0]`에 `budget_app` 폴더 자체가 등록됩니다.**
* 이로 인해 `budget_app` 폴더가 최상위 경로가 되므로 다음과 같은 심각한 임포트 에러가 발생합니다.
  1. **상대 임포트 에러:** `__main__.py`나 다른 모듈 내부에서 `from .models import Transaction`과 같이 점(`.`)을 찍는 상대 경로 임포트를 사용하는 경우, 파이썬은 이 폴더를 패키지로 인식하지 못하고 있으므로 **`ImportError: attempted relative import with no known parent package`** 에러를 던지며 즉시 중단됩니다.
  2. **절대 임포트 에러:** 만약 `import budget_app.models`와 같은 절대 경로 임포트를 시도하면, `sys.path` 상에는 `budget_app` 내부의 파일들만 노출되어 있고 `budget_app` 자체를 가리키는 부모 디렉토리가 없기 때문에 **`ModuleNotFoundError: No module named 'budget_app'`** 에러가 발생합니다.

#### (2) `python -m budget_app`으로 실행하는 경우 (모듈/패키지 실행)
`-m` 옵션은 "Module"의 약자로서, 파이썬에게 이 디렉토리를 **하나의 완성된 패키지**로 취급하여 실행할 것을 명령합니다.

* **`sys.path[0]`에 `budget_app` 폴더가 아닌, `budget_app`이 위치한 현재 작업 디렉토리(부모 폴더)가 등록됩니다.**
* 파이썬은 이 부모 폴더를 기준으로 `budget_app`이라는 패키지를 탐색해 들어가 내부의 `__main__.py`를 구동합니다.
* 따라서 패키지 내부 구조가 온전히 유지되므로, `from .models import ...` 같은 **상대 임포트**와 `import budget_app.models` 같은 **절대 임포트**가 모두 에러 없이 작동하게 됩니다.

### 2. "CSV는 리스트나 중첩 딕셔너리 표현이 극도로 까다로움"이라는데, 가능은 하다는 뜻인가요?

네, 기술적으로 구현 자체는 가능합니다. 다만 이를 구현하기 위해 치러야 하는 **아키텍처적 비용(비효율성과 리스크)이 매우 크다는 뜻**입니다.

CSV는 기본적으로 행(Row)과 열(Column)로만 구성된 2차원 평면 데이터 포맷입니다. 여기에 리스트나 중첩 딕셔너리를 구겨 넣으려면 크게 두 가지 우회 기법을 써야 합니다.

#### 방법 A. 문자열 직렬화(Serialization) 우회 방식
리스트나 딕셔너리를 하나의 문자열로 변환하여 하나의 CSV 셀(Cell) 안에 집어넣는 방법입니다.
* **리스트 예시:** 태그 리스트 `['외식', '식비']`를 `"외식|식비"` 또는 `"외식;식비"`와 같이 임의의 구분자(`|`, `;`)로 연결된 문자열로 저장합니다. 데이터를 읽을 때는 다시 해당 컬럼을 가져와 `.split('|')`로 쪼개는 코드를 작성해야 합니다.
* **딕셔너리 예시:** 중첩 구조를 아예 JSON 문자열로 변환하여 셀에 넣습니다.
  * 원본: `{"meta": {"ip": "1.2.3.4", "device": "mobile"}}`
  * CSV 저장 상태: `"{""meta"": {""ip"": ""1.2.3.4""}}"` (따옴표 이스케이프 필요)

> **⚠️ 문제점:** 
> 이 방식은 CSV 파싱 과정 외에 개발자가 데이터를 가공하는 코드를 수동으로 추가 작성해야 하므로 버그 발생률이 높아집니다. 또한, 사용자가 메모 칸에 실수로 구분자(`|`, `;`)나 따옴표를 기입하는 순간 파싱 규칙이 손상되어 전체 행 데이터가 밀리는 **데이터 파손**에 취약해집니다.

#### 방법 B. 데이터 평탄화(Flattening) 방식
중첩된 구조를 최상위 컬럼으로 모두 해체하여 평평하게 펼쳐 저장하는 방법입니다.
* **딕셔너리 예시:** `user: { name: "Kim", age: 30 }` 구조가 있다면, CSV 헤더를 `user_name`, `user_age`로 각각 쪼개어 컬럼을 증설합니다.

> **⚠️ 문제점:** 
> 만약 딕셔너리의 키가 동적으로 계속 변하거나(예: 사용자가 커스텀 메타데이터를 자유롭게 기입하는 경우), 리스트의 길이가 가변적이라면 사전에 고정된 CSV 헤더 스키마를 정의할 수 없게 되어 이 방식을 적용할 수 없게 됩니다.

따라서 이러한 구조적 복잡성을 해결하기 위해, 중첩 구조와 리스트 타입을 날것 그대로 안전하게 저장할 수 있는 **JSONL 포맷**을 선택하는 것이 합리적인 엔지니어링 의사결정이 됩니다.

### 3. mypy가 무엇이며, 타입 힌트가 '계약'이라는 표현은 비유인가요? 그리고 매개변수와 인자의 차이는 무엇인가요?

#### (1) `mypy`란 무엇인가요?
`mypy`는 파이썬 코드의 타입 일치 여부를 프로그램 실행 전에 검사해 주는 대표적인 **정적 타입 검사기(Static Type Checker)**입니다 [3.1.2]. 
파이썬 인터프리터 자체는 타입 힌트를 단순한 주석이나 힌트로 보고 실행 단계에서 무시하지만, `mypy` 같은 도구를 사용하면 마치 C언어나 Java처럼 빌드/실행 전에 타입 오류를 미리 찾아내어 걸러낼 수 있습니다 [3.1.2].

#### (2) '계약(Contract)'이라는 단어는 비유인가요?
**네, 파이썬의 '런타임(실행 단계)' 관점만 본다면 비유적인 표현이 맞습니다.**
실제로 파이썬 인터프리터는 아래와 같이 타입 힌트와 전혀 다른 타입의 값이 들어와도 에러를 내지 않고 그냥 실행합니다.

```python
def process_amount(amount: int) -> None:
    # 파이썬은 실행 시점에 amount가 str이어도 문법 에러를 내지 않습니다.
    # 단지 아래 연산 시점에 타입 에러가 날 뿐입니다.
    print(amount + 10) 

process_amount("만오천원") # 런타임에 아무 제지 없이 진입함
```

그러나 **'엔지니어링 협업 및 빌드 시스템'** 관점에서 타입 힌트는 **물리적이고 강제적인 계약**이 될 수 있습니다.
* 현업 백엔드 개발 프로세스에서는 코드를 서버에 배포하기 전, CI/CD 파이프라인이나 깃 커밋 직전 단계(`pre-commit`)에서 **`mypy` 검사를 필수 통과하도록 강제**합니다.
* 타입 오류가 1개라도 검출되면 배포 빌드가 실패(Fail)하도록 설정하기 때문에, 개발자는 마음대로 다른 타입의 값을 넘길 수 없게 됩니다. 따라서 현대 소프트웨어 공학에서 타입 힌트는 단순한 힌트를 넘어선 **배포 수준의 계약 체결**로 받아들여집니다.

#### (3) 매개변수(Parameter)와 인자(Argument)의 명확한 차이
이 두 용어는 자주 혼용되지만, 컴퓨터 과학적으로 명확한 차이가 존재합니다.

* **매개변수 (Parameter / 파라미터):**
  * **정의:** 함수의 **정의부(Signature)**에 선언된 변수를 뜻합니다. 값이 들어올 자리를 미리 마련해 둔 '틀' 혹은 '플레이스홀더'입니다.
  * **예시:** `def add(x, y):` 에서 `x`와 `y`가 매개변수입니다. 타입 힌트는 바로 이 매개변수에 선언됩니다.
* **인자 (Argument / 전달인자 / 아규먼트):**
  * **정의:** 함수를 실제 **호출할 때** 매개변수에 전달하는 '실제 값(실체)'을 의미합니다.
  * **예시:** `add(3, 5)` 에서 `3`과 `5`가 인자입니다.

> **정리하자면:** "개발자가 매개변수(Parameter)에 정의된 타입 계약을 위반하는 잘못된 인자(Argument)를 전달하려 할 때, `mypy`가 이를 사전에 감지하여 개발자에게 경고합니다."

### 4. 데이터베이스의 트랜잭션(Transaction) 사상이란 무엇인가요?

데이터베이스에서의 **트랜잭션(Transaction)**이란, **"더 이상 쪼갤 수 없는 업무 처리의 최소 단위"**를 의미합니다. 쉽게 말해 여러 개의 작업들을 하나의 묶음으로 처리하는 논리적 단위입니다.

예를 들어 'A가 B에게 1만 원을 송금하는 상황'을 생각해 봅시다. 여기에는 두 가지 작업이 동시 진행되어야 합니다.
1. A의 계좌에서 1만 원을 출금한다. (`UPDATE`)
2. B의 계좌에 1만 원을 입금한다. (`UPDATE`)

만약 1번은 성공했는데 컴퓨터가 다운되어 2번이 실패한다면, 세상에서 1만 원이 공중 분해되는 금융 대참사가 발생합니다. 이러한 비극을 막기 위해 트랜잭션 사상이 도입되었으며, 이는 **ACID**라 불리는 4가지 핵심 원칙을 지향합니다.

#### 1. 원자성 (Atomicity) — "All or Nothing"
* 트랜잭션 내의 모든 연산은 **전부 완벽히 성공하거나, 아니면 하나라도 실패할 경우 아예 아무것도 하지 않은 초기 상태로 되돌려야(Rollback)** 합니다. 어설프게 절반만 성공한 상태는 절대 허용하지 않는 성질입니다.
* 가계부 프로그램의 **원자적 쓰기(Atomic Write)**가 바로 이 사상을 구현한 것입니다. 데이터를 새로 쓰다가 에러가 나거나 정전이 되어 파일이 손상될 위험이 있다면, 아예 쓰기 전 상태를 보존하고, 정상 완료되었을 때만 새 파일로 한순간에 교체(`os.replace`)하여 "전부 성공" 또는 "전부 실패(이전 파일 보존)" 상태 중 하나만 남깁니다.

#### 2. 일관성 (Consistency)
* 트랜잭션이 성공적으로 완료된 후의 데이터베이스는 미리 정의된 모든 제약 조건(음수 잔액 금지, 데이터 유효성 등)을 완벽히 만족하는 일관된 상태여야 합니다.

#### 3. 격리성 (Isolation)
* 동시에 여러 트랜잭션이 실행될 때, 서로의 중간 연산 과정이 끼어들거나 간섭하지 못하게 격리 장벽을 치는 성질입니다. 한 작업이 완료될 때까지 다른 작업은 그 변경 사항을 볼 수 없습니다.

#### 4. 지속성 (Durability)
* 트랜잭션이 성공적으로 완료(Commit)되었다면, 그 결과는 시스템에 장애가 발생하더라도 영구적으로 보존되어야 합니다. (파일 시스템의 영구 디스크 동기화 과정 등이 이에 해당합니다.)

가계부 콘솔 프로그램에서 임시 파일(.tmp)을 생성하고 이를 최종 교체하는 일련의 과정은, 고가의 상용 RDBMS 없이도 로컬 파일 환경에서 데이터 트랜잭션의 **원자성(Atomicity)**과 **지속성(Durability)** 사상을 구현해 내기 위한 훌륭한 엔지니어링 기법입니다.

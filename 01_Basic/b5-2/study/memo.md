# 💡 파이썬 현미경 해설: `if __name__ == "__main__":`

## ❓ 질문
> `if __name__ == "__main__":` 코드는 왜 굳이 다른 곳에서 불려온(import) 걸 구분하나요? 왜 직접 실행할 때만 실행되도록 제한하는 거죠? 이 기능이 꼭 필요한 이유가 무엇인가요?

---

## 🔑 한 줄 요약
**"가져다 쓰기만 하려고 책을 폈는데, 책이 혼자서 갑자기 작동(실행)해버리는 대참사를 막기 위해서"** 입니다.

---

## 🔍 상세 설명

파이썬 파일(.py)은 크게 두 가지 용도로 사용됩니다.
1. **스크립트(Script)**: 터미널에서 직접 실행해서 동작을 수행하는 파일 (예: `python -m minigit`)
2. **모듈(Module)**: 다른 파일에서 클래스나 함수를 가져와서 재사용하기 위한 파일 (예: `import minigit`)

만약 `if __name__ == "__main__":` 조건문이 **없다면** 어떤 문제가 생기는지 알아봅시다.

### 1. 의도치 않은 코드 실행(Side Effect) 방지
파이썬은 어떤 파일을 `import` 하는 순간, **그 파일 안의 모든 코드를 위에서 아래로 한 번 쭉 실행**합니다.

만약 `minigit/__main__.py`에 다음과 같이 작성되어 있고 조건문이 없다면:
```python
# minigit/__main__.py
cli: MiniGitCLI = MiniGitCLI()
cli.run() # 조건문 없이 바로 실행!
```

다른 파일(예: `tests/test_minigit.py` 또는 완전히 다른 프로젝트)에서 `MiniGitCLI` 클래스를 테스트하거나 재사용하고 싶어서 단지 `import`만 했을 뿐인데:
```python
# test_minigit.py
from minigit.__main__ import MiniGitCLI # 단지 클래스를 가져오고 싶었을 뿐인데...
```
이 `import` 한 줄이 실행되는 순간, `cli.run()`이 강제로 실행되어 터미널 대기 상태에 빠지거나 실제 깃 명령어가 수행되어 버립니다. 

즉, **불러오기만(import) 하려고 했는데 강제로 프로그램이 대빵으로 실행되는 부작용**이 발생합니다.

### 2. 코드 재사용 및 테스트 가능성(Testability) 보장
단위 테스트(Unit Test)를 작성할 때는 소스 코드 파일에 정의된 클래스나 함수를 불러와서 하나씩 검증해야 합니다.
`if __name__ == "__main__":` 조건문을 두면:
* **직접 실행할 때**(`__name__`이 `"__main__"`일 때): CLI 인스턴스를 만들고 프로그램을 시작합니다.
* **다른 데서 불러올 때**(`__name__`이 파일/모듈 이름일 때): CLI 실행 부분은 건너뛰고, 오직 클래스 정의(`MiniGitCLI`)만 안전하게 읽어와서 가져갈 수 있게 해줍니다.

---

## 💡 요약
* **직접 실행할 때** ➡️ `__name__` 변수에 자동으로 `"__main__"`이라는 값이 대입됩니다.
* **가져다 쓸 때(import)** ➡️ `__name__` 변수에 실제 모듈 이름이 대입됩니다.
* 따라서 `if __name__ == "__main__":`을 사용하면 **"내가 이 파일을 직접 실행할 때만 실행 프로그램으로서 작동하고, 다른 데서 불러다 쓸 때는 얌전히 도구 상자(라이브러리) 역할만 해라"** 하고 명확하게 경계를 지어주는 역할을 합니다.

# 💡 파이썬 현미경 해설: `__repr__` 메서드

## ❓ 질문
> `__repr__`가 무엇이고 어떤 뜻인가요? 출력 결과는 어떻게 나오는지 예시로 보여주세요.

---

## 🔑 한 줄 요약
**"객체(Object)를 출력하거나 들여다볼 때, 사람이 읽기 쉬운 예쁜 문자열 형태로 바꿔주는 내장 함수"**입니다.

---

## 🔍 상세 설명

파이썬에서 우리가 만든 클래스로 객체를 생성한 뒤, 그냥 `print`로 출력해 보면 어떻게 될까요?
`__repr__`이 없는 상태에서 출력하면 파이썬은 다음과 같이 알아보기 어려운 기본값을 출력합니다.

```python
# __repr__이 없는 경우 출력 결과:
<minigit.models.Commit object at 0x104b2a3d0>
```
위 출력은 "minigit.models의 Commit 객체이고 메모리 주소는 0x104b2a3d0에 있다"라는 정보만 줍니다. 개발할 때 이 객체가 구체적으로 어떤 커밋 메시지를 담고 있는지, 해시는 무엇인지 전혀 알 수가 없어서 매우 불편합니다.

이때 **`__repr__` (Representation의 약자)** 함수를 정의해 주면, 객체를 문자열로 나타내야 할 때(예: `print(commit)`를 하거나, 디버거로 관찰할 때, 혹은 리스트에 담긴 객체를 출력할 때) 개발자가 지정한 예쁜 형식의 문자열로 대신 출력해 줍니다.

### 💻 코드 예시

```python
# Commit 클래스 안에 정의된 __repr__
def __repr__(self) -> str:
    return f"Commit(hash={self.hash}, message='{self.message}')"
```

### 📋 실제 출력 결과 예시

만약 아래와 같이 `Commit` 객체를 생성하고 출력하면:

```python
# 1. 커밋 객체 생성
my_commit = Commit(
    message="Initial commit",
    author="Gildong",
    timestamp=1686979200.0,
    parents=None
)

# 2. 객체 출력하기
print(my_commit)
```

**콘솔 출력 화면:**
```text
Commit(hash=a3f5c2, message='Initial commit')
```

개발자는 이제 메모리 주소 대신 **해시값(`hash`)**과 **커밋 메시지(`message`)**를 바로 직관적으로 확인할 수 있게 됩니다!

### 💡 꿀팁: `__str__`과의 차이점
* **`__repr__`**: 주로 **개발자**가 디버깅할 때 객체의 명확한 상태를 확인하기 위한 목적으로 사용됩니다. (리스트 안에 담긴 객체들을 출력할 때도 이 `__repr__`이 실행됩니다.)
* **`__str__`**: 주로 **사용자**에게 보여주기 위한 친절하고 예쁜 텍스트로 바꿀 때 사용됩니다. (`print()`나 `str()`로 직접 감쌌을 때 우선적으로 호출됩니다.)
* 보통 `__str__`을 구현하지 않으면 파이썬은 `__repr__`을 대신 호출하기 때문에, 개발 시에는 `__repr__` 하나만 잘 구현해 두어도 두 목적을 모두 달성할 수 있어 매우 유용합니다.

# 💡 파이썬 현미경 해설: `Repository` 클래스의 `__init__` vs `init`

## ❓ 질문
> `Repository` 클래스 안에 왜 `__init__` 함수와 `init` 함수가 따로 구분되어 있나요? 둘 다 빈 값의 기본값 틀을 생성하는 느낌인데, 굳이 `init`이 필요한 이유가 무엇인가요?

---

## 🔑 한 줄 요약
* **`__init__`**: **파이썬 언어 차원**에서 객체(메모리 공간)를 새로 만들 때 자동으로 호출되는 "생성자"입니다.
* **`init`**: **MiniGit 프로그램 기능 차원**에서 사용자가 터미널에 `git init`을 쳤을 때 실행되는 "저장소 초기화 비즈니스 로직"입니다.

---

## 🔍 상세 설명

두 함수는 이름이 비슷하고 멤버 변수를 비우거나 생성하는 코드가 겹쳐서 헷갈릴 수 있지만, **역할과 호출 시점**이 완전히 다릅니다.

### 1. `__init__(self)` (파이썬 기본 생성자)
* **역할**: 파이썬 메모리상에 `Repository`라는 객체를 생성할 때, 변수들(commits, branches, head 등)의 **자리(공간)를 만들어두는 역할**입니다.
* **호출 시점**: `repo = Repository()` 코드를 실행하여 객체를 생성할 때 파이썬에 의해 **자동으로 딱 한 번 실행**됩니다.
* **특징**: 이 단계에서는 아직 사용자가 누구인지(`current_user`) 지정되지 않았고, 실제 사용 가능한 Git 저장소 상태가 아닙니다. (`self.initialized = False`)

### 2. `init(self, user_name: str)` (MiniGit 저장소 초기화 메서드)
* **역할**: 실제 사용자가 터미널에 `minigit init <이름>` 명령어를 쳤을 때 **"이 이름을 쓰는 새 Git 저장소를 가동하겠다!"**라고 선언하는 비즈니스 기능입니다.
* **동작 내용**:
  1. 기존에 있던 정보들을 깨끗이 초기화(reset)합니다.
  2. 기본 브랜치인 `main`을 생성하고 등록합니다 (`self.branches['main'] = None`).
  3. 현재 사용자를 등록합니다 (`self.current_user = user_name`).
  4. 이제 저장소가 정상적으로 초기화되어 준비 완료되었다고 도장을 찍어줍니다 (`self.initialized = True`).
* **만약 `init` 메서드가 없다면?**
  * 사용자가 터미널에서 아무리 `minigit init`을 하려고 해도, 사용자 이름을 받아 저장소를 활성화하는 행동을 할 수 없습니다. `__init__`은 사용자 입력을 받아 저장소를 세팅하는 기능이 아니라, 단순 객체 껍데기 생성용이기 때문입니다.

---

## 💡 요약 비교표

| 구분 | `__init__` | `init` |
| :--- | :--- | :--- |
| **성격** | 파이썬 언어 시스템의 생성자 | MiniGit 프로그램의 사용자 명령어 처리기 |
| **호출 방법** | `repo = Repository()` (자동 호출) | `repo.init("Gildong")` (직접 호출) |
| **목적** | 메모리에 객체 껍데기 만들기 | 사용자 이름 등록 및 실질적인 저장소 사용 시작 (`initialized = True`) |
| **초기화 완료 여부** | `initialized = False` (아직 사용 불가) | `initialized = True` (이제 커밋 등 가능) |

# 💡 파이썬 현미경 해설: '비즈니스 로직'과 '초기화 시 메모리 변화'

## ❓ 질문
1. **'비즈니스 로직'**이라는 말이 굉장히 낯선데, 코딩에서 쓰는 관용어인가요? 왜 이런 이름이 붙었나요?
2. 프로그램 내부에서 `init` 명령어를 실행(다시 초기화)하면 **기존에 메모리에 있던 데이터는 제거되나요?** 어떻게 처리되나요?

---

## 🔑 한 줄 요약
1. **비즈니스 로직**: 꼭 상업적인 의미가 아니라, **"프로그램이 해결해야 하는 현실의 업무 규칙/요구사항을 담은 핵심 코드"**를 뜻하는 소프트웨어 공학 표준 용어입니다.
2. **메모리 제거**: `Repository` 객체 자체는 사라지지 않지만, 내부 변수들을 빈 값으로 덮어씌우면서 **기존의 쓸모없어진 옛날 데이터들은 파이썬이 알아서 메모리에서 자동으로 지워줍니다(가비지 컬렉션)**.

---

## 🔍 상세 설명

### 1. 💼 개발 용어: '비즈니스 로직(Business Logic)'의 유래
개발자들이 "이건 비즈니스 로직이야"라고 할 때의 **'비즈니스(Business)'**는 '사업'보다는 **'업무(Task) 또는 해결해야 할 도메인 문제'**에 가깝습니다.

* **비즈니스 로직 (Core Domain Logic)**:
  * 프로그램의 **본질적인 기능과 규칙**을 뜻합니다.
  * *예: MiniGit의 경우* ➡️ "저장소를 초기화한다", "커밋을 하면 SHA-1 해시를 생성해 중복 검사를 한다", "브랜치를 생성한다" 등.
  * *예: 쇼핑몰의 경우* ➡️ "상품 가격이 5만 원 이상이면 배송비를 무료로 처리한다", "쿠폰 할인율을 적용해 최종 결제 금액을 계산한다" 등.
* **그 외의 로직 (Infrastructure / System / UI Logic)**:
  * 비즈니스 로직을 보조하기 위해 시스템 뒤에서 돌아가는 코드입니다.
  * *예* ➡️ 화면에 텍스트 색상을 빨간색으로 그리기, 객체 생성을 위해 변수 공간 잡기(`__init__`), DB 연결하기 등.

따라서 `Repository.init`은 MiniGit의 핵심 업무 규칙(저장소 활성화, main 브랜치 생성 등)을 다루므로 **비즈니스 로직**이라고 부릅니다.

---

### 2. 🧠 `init` 실행 시 메모리는 어떻게 변하나요?
`Repository.init` 함수 내부를 보면 다음과 같은 코드가 있습니다.

```python
self.commits = {}
self.branches = {}
```

이 코드가 실행될 때 메모리에서는 아래와 같은 일이 일어납니다.

1. **기존 객체는 유지**: `Repository` 인스턴스(객체) 자체는 메모리 상에서 없어지지 않고 그대로 살아있습니다.
2. **참조 끊기**: `self.commits`가 가리키고 있던 기존의 수많은 커밋 데이터 딕셔너리와의 연결을 끊고, **완전히 새로운 빈 딕셔너리 `{}`**를 가리키게 만듭니다.
3. **가비지 컬렉션(Garbage Collection) 작동**: 
   연결이 끊겨서 메모리 한구석에 둥둥 떠다니는 옛날 커밋 데이터들은 **"더 이상 아무도 사용하지 않는 쓰레기 데이터"**가 됩니다. 파이썬의 청소부 역할인 **가비지 컬렉터(Garbage Collector)**가 이 쓰레기들을 감지하고 자동으로 메모리에서 지워버립니다.

결과적으로, 기존 메모리는 안전하게 회수되고 새롭게 깨끗해진 상태로 저장소가 다시 태어나게 됩니다!

# 💡 파이썬 현미경 해설: `TYPE_CHECKING`과 순환 참조(Circular Import)

## ❓ 질문
> `TYPE_CHECKING`이 무엇이고 순환 참조 에러와는 어떤 관계인가요?

---

## 🔑 한 줄 요약
* **순환 참조(Circular Import)**: 두 파일이 서로를 불러와서(`A ➡️ import B`, `B ➡️ import A`) 파이썬이 로딩에 실패하고 뻗는 에러입니다.
* **`TYPE_CHECKING`**: **"실제 프로그램이 실행될 때는 import를 생략하고, 에디터(VS Code 등)가 코드 검사/자동완성을 할 때만 import를 허용"**하여 순환 참조를 막아주는 방패입니다.

---

## 🔍 상세 설명

### 1. 🔄 순환 참조(Circular Import) 에러란?
파이썬은 파일을 위에서 아래로 순차적으로 읽으며 실행합니다. 이때 두 파일이 서로를 끌어다 쓰려고 하면 무한 굴레에 빠집니다.

* **상황 예시**:
  1. `models.py`에서 "이메일 발송 도구"를 쓰려고 `import email_sender`를 합니다.
  2. `email_sender.py`에서도 이메일을 보낸 사람 정보를 모델로 표시하고 싶어서 `from models import User`를 합니다.
  3. **결과**: 파이썬은 `models.py`를 읽다가 `email_sender`로 넘어가고, 거기서 다시 `models`를 부르는 순간 **"아직 models가 다 로딩 안 됐는데 또 불러?!"** 하며 `ImportError`를 냅니다.

### 2. 🛡️ 마법의 방패: `TYPE_CHECKING`
타입 힌트(예: `commit: Commit`)를 쓰고 싶은데, 정작 실제 코드 실행할 때는 순환 참조가 날 때 이 방패를 씁니다.

`TYPE_CHECKING`은 `typing` 모듈에서 제공하는 특별한 상수(boolean)로 다음과 같이 작동합니다.
* **실제 프로그램을 실행할 때 (Runtime)**: `TYPE_CHECKING`은 항상 `False`가 됩니다.
* **에디터(VS Code, PyCharm 등)가 코드를 검사할 때 (Static Analysis)**: `TYPE_CHECKING`은 `True`가 됩니다.

```python
# 예시 코드
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    # 💡 에디터가 검사하고 자동완성을 띄워줄 때만 여기를 읽습니다!
    # 실제 프로그램이 돌 때는 이 코드가 통째로 무시됩니다.
    from minigit.models import Commit 
```

이렇게 하면, **실제 실행 시점에는 `import`를 안 하므로 순환 참조 에러가 전혀 나지 않으면서도**, 우리가 코드를 작성할 때는 **에디터가 타입을 인식해 주기 때문에 완벽한 자동완성과 빨간 줄(타입 에러) 검사를 받을 수 있게 됩니다.**

# 💡 파이썬 현미경 해설: `deque` vs `list` & LCS 알고리즘

## ❓ 질문
1. **`deque`**는 무엇인가요? 일반 `list`를 만들어서 하나씩 빼 쓰는 것과 성능상/근본적인 차이가 있나요?
2. `diff.py`에서 **`compute_lcs_table`** 함수는 오직 `diff_files`만을 위해 존재하나요? 그리고 **LCS**의 뜻은 무엇인가요?

---

## 🔑 한 줄 요약
1. **`deque` (데크)**: **"앞과 뒤 양쪽 모두에서 매우 빠르게 자료를 넣고 뺄 수 있는 더블 엔디드 큐(Double-Ended Queue)"**입니다. 일반 `list`에서 맨 앞 요소를 뺄 때(`pop(0)`) 발생하는 속도 저하를 완벽하게 해결합니다.
2. **LCS (Longest Common Subsequence, 최장 공통 부분 수열)**: 두 텍스트에서 **"순서를 유지하면서 공통으로 겹치는 가장 긴 줄 목록"**을 뜻합니다. `compute_lcs_table`은 오직 파일 비교(`diff_files`)에서 줄 바꿈 차이(+, -)를 계산하기 위해 테이블을 그리는 내부 도구로 사용됩니다.

---

## 🔍 상세 설명

### 1. 📦 일반 `list` vs `collections.deque`

파이썬의 `list`도 큐(Queue)처럼 사용할 수 있지만, **맨 앞의 값을 뺄 때 성능 차이**가 아주 심하게 납니다.

* **일반 `list` (동적 배열)**:
  * 리스트는 메모리에 칸들이 다닥다닥 나란히 붙어있습니다.
  * 맨 끝에 요소를 추가(`append`)하거나 빼는(`pop`) 것은 엄청 빠릅니다($O(1)$).
  * 하지만 맨 앞의 요소를 빼내면(`pop(0)`), 빈자리를 채우기 위해 **뒤에 있는 모든 데이터들을 앞으로 한 칸씩 다 밀어서 이사시켜야** 합니다.
  * 즉, 데이터가 $N$개일 때 맨 앞을 빼는 작업은 $O(N)$만큼 느려집니다. 데이터가 많아지면 프로그램이 심각하게 버벅거립니다.
* **`deque` (이중 연결 리스트)**:
  * `deque`는 칸들이 메모리에 흩어져 있고, 앞뒤 노드끼리 서로 가리키는 화살표(링크)로 연결되어 있습니다.
  * 맨 앞 요소를 빼내도(`popleft`), 다음 사람한테 "이제 네가 맨 앞이야"라고 화살표만 바꾸면 끝입니다.
  * 따라서 맨 앞을 빼는 작업도 일반 `list`와 달리 **항상 엄청 빠릅니다($O(1)$)**.
  * BFS(너비 우선 탐색)처럼 **큐에 데이터를 넣고 맨 앞부터 순서대로 계속 꺼내 쓰는 알고리즘**을 쓸 때는 무조건 `deque`를 써야 성능 문제를 피할 수 있습니다.

---

### 2. 📝 LCS와 `compute_lcs_table`

* **LCS(최장 공통 부분 수열)**란?
  * 두 문서가 있을 때, 중간에 글이 새로 추가되거나 삭제되었더라도 **흐름상 공통으로 겹치는 가장 긴 줄들**을 의미합니다.
  * 예를 들어, `A = [가, 나, 다]`, `B = [가, 라, 다]` 가 있을 때 LCS는 `[가, 다]`가 됩니다.
  * Git의 파일 비교(`diff`)는 이 LCS를 구하는 것에서 출발합니다. **"가장 많이 공통으로 겹치는 뼈대(LCS)를 발라내고, 뼈대에 속하지 않는 나머지는 추가(+)되거나 삭제(-)된 줄로 판별하자"**는 아이디어입니다.
* **`compute_lcs_table`은 `diff_files`를 위해서만 존재하나요?**
  * **네, 맞습니다.** 전체 코드에서 `compute_lcs_table`은 `diff.py` 내부의 `compute_diff` 함수(LCS 테이블을 역추적해 `+`, `-` 기호를 붙여주는 함수)에서만 호출되고 있습니다. 
  * 코드의 가독성을 높이고 역할을 쪼개기 위해 **"LCS 테이블을 만드는 기능(`compute_lcs_table`)"**과 **"테이블을 기반으로 실제 `+ / -` 차이점을 조립하는 기능(`compute_diff`)"**을 분리해서 작성해 둔 것입니다.

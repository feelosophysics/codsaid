# Mini Git 리팩토링 가이드

이 문서는 B5-2 Mini Git을 읽고 검토할 때 사용하는 판단 기준이다. 목표는 **요구사항에 맞는 동작을, 학습자가 입력·상태 변화·알고리즘과 연결해 이해할 수 있는 작은 코드로 표현하는 것**이다. 클래스 수나 줄 수가 설계의 품질을 결정하지 않는다.

현재 학습 목표는 기존 코드를 보고 각 부분의 역할과 실행 흐름을 대략 설명하는 것이다. 프레임워크 설계를 배우는 수준을 전제하지 않는다. 이 문서는 현재 구현을 정답으로 승인하는 문서가 아니며, 검토 결과에 따라 갱신한다.

## 1. 판단의 우선순위

1. **미션의 동작과 제약을 지킨다.** 부모 우선 LOG, 무방향 최단 경로와 문자열 사전순 동률 처리, 조상 탐색, 역색인, 직접 구현한 정렬이 먼저다.
2. **재현한 오류와 실제 위험을 해결한다.** 잘못된 입력이 상태를 망가뜨리거나 프로그램을 종료시키는지 확인한다. 영향과 발생 경로를 함께 설명한다.
3. **흐름을 쉽게 읽을 수 있게 한다.** 명령 하나가 어떤 함수를 거쳐 어떤 데이터를 바꾸는지 따라갈 수 있어야 한다.
4. **같은 규칙을 함께 관리하고 불필요한 구조를 줄인다.** 중복 제거가 새 간접 호출과 설명 부담을 늘리는지도 비교한다.

미션의 정렬·탐색·인덱싱은 학습 대상이므로 직접 구현한다. 표준 정렬 API와 그래프 전용 라이브러리의 금지는 유지한다. 파일 내용 추적·네트워크·영속 저장은 필수 범위가 아니다. 보너스 기능은 필수 기능과 구분한다. 이미 제공하는 기능을 삭제할 때는 학습 범위와 사용자 의도를 확인한다.

## 2. 필요한 코드와 추상화

함수·클래스·모듈·상수를 추가할 때는 현재 요구사항, 실제 중복, 재현한 오류 중 무엇을 해결하는지 설명한다. 이름을 붙인 뒤 호출부의 의도가 더 명확해지는지, 오히려 더 많은 파일과 호출을 따라가야 하는지 비교한다.

한 번 쓰는 코드도 복잡한 알고리즘이나 분명한 책임을 표현하면 함수로 분리할 이유가 있다. 반대로 한 줄을 감싸고 원래 이름만 바꾼 도우미는 효과가 없다면 만들지 않는다. 아직 없는 확장을 위한 기반 클래스·플러그인 체계·범용 명령 프레임워크는 도입하지 않는다.

**같은 모양과 같은 규칙을 구분한다.** 여러 명령의 인자 수 검사처럼 함께 바뀌어야 하는 규칙은 공통화할 후보지만, 짧은 검사 몇 줄을 줄이려고 옵션·상태·오류 우선순위를 복잡한 설정 표로 옮기지는 않는다. 공통화 후에도 각 명령의 규칙이 보이는지 확인한다.

## 3. 책임과 데이터 흐름

- CLI는 문자열 파싱, 명령 선택, 사용자에게 보여줄 결과를 담당한다.
- 저장소는 커밋·브랜치·HEAD·작성자 상태와 그 상태의 변경 규칙을 담당한다.
- 그래프·정렬 함수는 경로나 순서를 계산한다. 계산하면서 원본 커밋을 변경할 필요는 없다.
- 역색인은 검색 후보를 얻기 위한 표이며 커밋 생성 시 저장소와 함께 갱신한다.

상태와 그 상태를 다루는 동작이 함께 있는 `Repository`·`InvertedIndex`에는 클래스가 어울린다. 상태 없는 탐색·정렬에는 함수가 충분할 수 있다. 파일로 나누려는 이유만으로 클래스를 만들지 않는다.

커밋 생성·브랜치 전환은 상태 변경이 기능의 목적이다. 이를 억지로 순수 함수로 바꾸지 않는다. 무엇을 바꾸는지 드러내고, 실패한 요청은 변경 전에 종료하도록 한다. 커밋 저장·브랜치 끝 이동·색인 갱신처럼 함께 일어나야 하는 변경을 확인한다.

작은 CLI에서 저장소 메서드가 출력 문자열을 반환하는 방식은 단순할 수 있다. 다만 저장소와 화면 표현이 연결된다는 비용을 인정한다. 출력 재사용이나 테스트에 실제 문제가 생기면 데이터 반환과 문구 생성을 분리한다. 모든 명령에 별도의 결과 객체를 먼저 만들 필요는 없다.

## 4. 입력 검사와 예외 처리

정제·검사·실행의 순서를 의식하되, 모든 함수에 세 개의 별도 단계나 도우미를 강제하지 않는다. 입력의 의미를 바꾸지 않는 정제만 수행한다. 검색 단어를 소문자로 만드는 규칙을 사용자 메시지나 파일 경로 전체에 그대로 적용하지 않는다.

검사는 **판단할 정보가 갖춰진 지점**에 둔다. 인자 수는 파싱 후, 브랜치 존재 여부는 저장소 상태에서, 파일 읽기 오류는 파일을 읽는 지점에서 다룬다. early return은 들여쓰기를 줄이는 수단이며 모든 예외를 함수 첫 줄에서 처리하라는 뜻이 아니다.

CLI의 문법 검사와 저장소의 상태 검사는 서로 다른 책임이다. 같은 검사를 여러 층에서 반복하기 전에는 그 함수를 CLI 밖에서도 직접 호출하는지와 그 함수가 보장할 계약을 확인한다. 타입 힌트만으로 입력이 자동 검증되지는 않는다.

예상 가능한 오류는 구체적으로 처리한다. 닫히지 않은 따옴표, 빈 인자, 없는 브랜치·커밋, 잘못된 경로, 파일 접근 실패, UTF-8 해석 실패 등이 대상이다. `except Exception`으로 모든 실패를 성공 문구나 빈 결과로 덮지 않는다. 구현상의 결함과 사용자가 고칠 수 있는 입력 오류를 구분한다.

보안 검토는 이 프로그램의 실제 경계에서 수행한다.

- 입력 문자열을 `eval`이나 운영체제 명령으로 실행하지 않는다. 토큰으로 나누는 것과 명령을 실행하는 것은 다르다.
- 외부 파일·메시지를 터미널에 보여줄 때 제어문자의 영향을 확인한다. 저장 데이터와 출력 표현을 구분한다.
- 큰 파일과 LCS 표처럼 입력에 따라 자원을 많이 쓰는 부분은 읽기·할당 전에 상한을 확인하고 초과 이유를 설명한다. DIFF에 상한을 두는 것은 사용자가 선택한 방향이다. 현재 구현은 파일당 1,048,576바이트, LCS 표 1,000,000칸이며 수치는 구현과 문서에서 일치시킨다.
- 로컬 학습용 CLI에 없는 원격 서버·인증·권한 체계를 가정하여 코드를 추가하지 않는다. 사용자가 지정한 파일을 읽는 기능 자체와 의도하지 않은 실행·출력 효과를 구분한다.

## 5. 문법과 표현

| 대상 | 판단 기준 |
| --- | --- |
| 이름 | 역할과 의미를 드러낸다. 알고리즘의 `i`, `j`, LCS의 `dp`처럼 문맥상 명확한 이름도 허용한다. 이름을 길게 만드는 것 자체가 목적은 아니다. |
| 타입 힌트 | 함수의 입력·출력과 복잡한 자료구조에 우선 사용한다. 추론 가능한 모든 지역 변수에 반복하지 않는다. Python 3.10의 `list[str]`, `dict[str, Commit]`에 `typing` 임포트는 필요하지 않다. |
| early return | 실패 조건이나 종료 조건을 먼저 끝내 흐름을 평평하게 한다. 이후 실행이 불가능해졌다면 불필요한 `else`를 붙이지 않는다. |
| `if`·`elif`·`else` | 서로 배타적인 선택과 독립적인 검사를 구분한다. 모든 분기에 세 문법을 갖출 필요는 없다. |
| 컴프리헨션 | 간단한 변환·필터는 읽기 쉬우면 허용한다. 중첩·상태 변경·여러 조건이 섞이면 루프를 사용한다. 학습 대상 알고리즘의 중간 상태가 중요한 구간은 명시적인 루프를 우선한다. |
| 조건식 | 짧은 값 선택은 읽기 쉬우면 허용한다. 중첩하거나 긴 처리를 숨기지 않는다. |
| 상수와 문자열 | 반복되는 정책값·공유 문구·의미가 불분명한 값에 이름을 붙인다. `0`, `1`, 빈 목록·문자열, 가까이서 의미가 보이는 키와 단발 문구를 모두 다른 파일로 이동시키지 않는다. |
| `Enum`과 텍스트 클래스 | 구분된 상태나 공유 문구를 관리하는 데 도움이 될 때 사용한다. 모든 문자열을 객체로 바꿀 의무는 없다. 기존 텍스트 클래스도 호출부의 가독성을 기준으로 평가한다. |
| 주석과 docstring | 주요 함수의 역할·계약, 알고리즘 선택 이유, 경계 조건과 제한을 설명한다. `append`가 추가한다는 설명을 모든 줄에 반복하지 않는다. 학습용 문법 설명은 처음 필요한 곳이나 학습 자료에 둔다. |

## 6. 표준 도구를 선택하는 예: `shlex`

미션은 공백을 포함한 인자를 따옴표로 묶도록 요구한다. `COMMIT "Add login feature"`는 명령과 메시지, 두 토큰이 되어야 한다. 일반 `str.split()`은 따옴표의 의미를 처리하지 못한다.

`shlex`는 간단한 명령 문법과 따옴표가 있는 문자열을 토큰으로 나누는 표준 라이브러리다. 파싱 자체가 학습 목표가 아닌 이 미션에서는 직접 따옴표 파서를 만드는 것보다 필요한 코드를 줄일 수 있다. 유일한 선택인 것은 아니지만 현재 요구에는 사용할 근거가 있다.

현재 `parse_input()`의 설정은 각자 다음 역할을 가진다. 삭제하거나 단순한 `shlex.split()`으로 교체할 때는 이 동작을 보존하는지 확인한다.

| 설정 | 현재 구현에서 필요한 이유 |
| --- | --- |
| `posix=True` | 묶음에 쓰인 따옴표를 제거하고 인자 중간의 따옴표도 처리한다. `SEARCH --author="Alice Lee"`가 한 옵션 토큰으로 나온다. |
| `whitespace_split=True` | 공백을 토큰 경계로 사용해 옵션·경로의 문장부호를 별도 토큰으로 쪼개지 않는다. |
| `commenters = ""` | 메시지나 인자의 `#` 뒤를 주석으로 버리지 않는다. |
| `escape = ""` | Windows 경로의 역슬래시를 보존한다. 대신 이 CLI에서 역슬래시를 사용하는 따옴표 이스케이프는 지원하지 않는다는 제한을 문서화한다. |

이 코드는 Windows 셸 명령을 만들거나 실행하지 않는다. `shlex`의 토큰 분리와 Windows 셸에서 안전한 인용을 같은 문제로 취급하지 않는다. 동작 근거는 [Python 3.10의 shlex 공식 문서](https://docs.python.org/3.10/library/shlex.html)를 참고한다.

## 7. 검토·변경·검증 순서

1. **구현과 미션을 대조한다.** 학습 원리, 미션의 특별 규칙, 현재 구현만의 선택을 구분한다.
2. **문제를 재현한다.** 발생 조건·실제 결과·기대 결과를 기록한다. 단순한 취향 차이를 취약점으로 부르지 않는다.
3. **가장 작은 유용한 변경을 고른다.** 오류 수정, 중복 제거, 구조 변경의 이유를 구분한다. 더 많은 추상화와 더 적은 코드로 해결하는 것을 비교한다.
4. **변경을 검증한다.** 기존 정상 동작과 재현 사례를 확인한다. 우발적인 구현 순서 대신 미션이 요구하는 결과를 검사한다.
5. **관련 자료를 맞춘다.** 코드·README·학습 가이드가 설명하는 호출과 동작이 일치해야 한다. 기존 코드의 실행을 재현했다는 사실만으로 그 설계가 좋은 본보기라고 결론 내리지 않는다.

주요 검증 사례는 첫 커밋·빈 저장소·브랜치 분기·재초기화, 부모가 둘인 그래프, 동일 출발·도착점과 연결 없는 경로, 사전순 동률, 공통 조상 중복, 검색 정규화·구절·문장부호, 정렬 동률, 잘못된 입력 이후 REPL 계속 실행, 파일 오류와 자원 상한이다.

오류 수정에는 재현 사례를 회귀 테스트로 남긴다. 동작을 바꾸지 않는 문서 수정이나 단순 이름 변경마다 구현을 그대로 따라 하는 테스트를 추가하지 않는다. 성능 수치는 환경에 따라 달라지므로 우승 알고리즘이나 실행 시간을 고정된 정답으로 검사하지 않는다.

## 8. 가이드가 부패하지 않게 유지하기

이 문서는 특정 에이전트에 대한 명령 모음이나 현재 코드의 영구적인 승인이 아니다. 프로젝트에서 판단할 근거를 공유하는 문서다.

- 미션의 필수 제약, 사용자의 학습 선호, 일반적인 설계 권고를 구분한다. 선호를 보편적인 금지 규칙으로 승격하지 않는다.
- 새 규칙은 해결하려는 문제와 적용 범위가 있을 때 추가한다. 다른 항목과 중복되면 기존 항목을 다듬는다.
- 구현의 제한이 바뀌면 관련 설명을 확인한다. 코드에 없는 기능·안전장치·검증 결과를 이미 있는 것처럼 적지 않는다.
- 리뷰마다 관련 항목을 점검하되 코드나 문서를 전부 다시 작성하지 않는다. 더 이상 도움이 되지 않는 규칙과 예시는 삭제하거나 고친다.
